## このプロジェクトで実現する利益

- リグレッションテストを自動化し、サービスに必要な機能が実環境で動作することを素早く確認する。
- これによりリリースに対する心理的障壁をなくし、高頻度のリリースを実現する。

## テストベース（何をテストするか）

- dev、stg、prodの各環境にデプロイされたプロダクトコードが、実際のネットワークおよびインフラで動作すること。
  - テスト対象のサイトは本番環境のみだが、実務においてはこの方針。

- プロダクトコードと環境の連動を確認するのが目的であるため、ビジネスプロセスの網羅は行わない。
  - C0カバレッジを達成するイメージ。

## 実装の方針

- ワークフロー単位でテストを実装する。
  - 例：ユーザーの新規作成に対するテストを自動化する場合、『作成成功』のパターンのみ自動化する。
    - 『作成失敗』に対するテストは作成しない。パターン網羅はMedium/Smallのテストで行う前提。

- 静的な文言に対するテストは行わない。ロジックと同様、より小さいサイズで行うことが望ましいため。
  - 特定の文言をexpectの対象にして『操作が成功したこと』を確認するのはOK。

- 実装の詳細はPlaywright公式のベストプラクティスに準拠する。
  - https://playwright.dev/docs/best-practices
  - 日本語訳版：https://daipresents.com/2024/04/15/playwright-best-practices/

## 実施の方針

- 実施タイミングは手動 → GitHub Actionsでの自動実行へと段階的に移行する。
  - 実装の初期は動作が安定しないため。
  - devでの実施は要検討。作業ブランチのマージ時にLarge(Playwright)のテストを毎回実行するのは過剰かもしれない。安定性と速度による？
